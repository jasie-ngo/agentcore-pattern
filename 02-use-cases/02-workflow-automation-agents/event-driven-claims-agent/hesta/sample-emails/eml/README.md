# `.eml` fixtures (real attachments)

These are real MIME `.eml` files — one per intent, plus three failure cases —
generated by `scripts/generate_sample_emails.py::build_eml_fixtures()`. They
exercise the TODO 2–5 attachment pipeline end to end: the Trigger Lambda parses
the MIME parts, the normalizer carries the real `attachments` list, and the
deterministic validator (`forms/parser.py` + `agents/attachment_validation.py`)
matches the attached form against the intent and checks its fields.

Unlike the sibling `.txt` fixtures (which use the `[ATTACHMENT FILENAME]` text
marker or no attachment concept at all), every file here is a genuine
`multipart/mixed` email with a `text/plain` body and, where noted, a
`text/plain` attachment encoded `Content-Transfer-Encoding: 7bit` — open any of
them in a text editor; the attachment is plain, human-readable, greppable text,
never base64.

Each filled fixture's sender (`From:`) matches the corresponding seed member in
`scripts/seed_hesta_members.py`, so identity verification succeeds the same way
it does for the `.txt` samples.

## Regenerating

```bash
python3 scripts/generate_sample_emails.py
```

Regeneration is idempotent — the only byte-level difference between runs is the
random MIME boundary string; `git diff` on these files should otherwise be empty.

## Dropping one into S3 (manual test)

```bash
aws s3 cp hesta/sample-emails/eml/BDBN_60010001_filled.eml \
  s3://<inbox-bucket>/claims-inbox/BDBN_60010001_filled.eml
```

The existing EventBridge rule (`object.key` prefix `claims-inbox/`) picks it up
and invokes the Runtime exactly as it does for the `.txt` samples — no
infrastructure change is needed to test a `.eml` drop.
